# Voice, identity use, and application to other media

Sources: [home template](source/web/index.ejs), [about](source/web/about.ejs), [blog](source/web/blog.ejs), [guestbook](source/web/guestbook.ejs), [journal](source/web/journal.ejs), [header](source/web/partials/header.ejs), [footer](source/web/partials/footer.ejs), [Starship](source/rice/starship.toml). These are observations of the user's own existing presentation, not an inferred psychological profile or invented marketing platform.

## Observable language

The header identifies the owner as a software engineer and builder. Pages use first-person writing and direct address. Existing copy mixes ordinary sentences with lowercase asides, parentheticals, abbreviations, smileys, and informal jokes. The site explicitly presents itself as the center of the owner's online presence in the about text. The user also explicitly describes fl1nt.dev as a personal brand, which is the scope of this skill.

| Observed device | Evidence/example | Appropriate reuse |
|---|---|---|
| Personal introduction | Home starts `Hey, I'm` | Direct, human introduction when the artifact actually introduces the owner |
| Code-comment headings | `// Projects`, `// Recent Posts`, `// Entries` | Section labels, operational readouts, title markers |
| Shell/path language | `about_flint.sh`, `whoami --verbose`, `~/journal.log` | Contextual terminal/file metaphors, not meaningless syntax on every sentence |
| Bracket labels | Username/IRL labels; Starship readout format | Compact secondary metadata or state indicators |
| Informal aside | Blog topics include `programming (obviously)` | Occasional relevant conversational aside |
| Casual interface humor | Decorative blog-tab tooltip admits it is there for the effect | Use sparingly where it does not conceal functionality |
| Community invitation | Guestbook asks visitors to sign and optionally link a site | Plain, personal participation copy |
| Personal-web affiliation | Webring, shareable button, live chat and guestbook | Community/linkback features when actually part of the task |
| Self-tracking | Journal calendar, compact weather/music/commit/mood readouts | Real, relevant data with clearly labeled units/status |

Do not fabricate new biographical statements, interests, personal beliefs, employment, location, status, or emotional data. Captured page data is dated evidence, not evergreen copy. Do not import guestbook messages as the owner's voice. Special-experience narrative fragments are source content, not verified facts about every future brand application.

## Casing and punctuation

There is no all-lowercase rule. Navigation is styled lowercase. Status labels, filters, widget titles, and many buttons are uppercase. Editorial headings and prose use mixed case. Journal buttons are styled lowercase, while guestbook submit retains its own casing. Preserve this division between compact labels and readable content.

`//`, `[ ]`, `>`, paths, filenames, arrows, and code punctuation have concrete uses. They provide a recognizable text vocabulary without needing unrelated circuit diagrams, binary rain, invented hacker slogans, or extra pseudo-technical terminology.

## Application beyond the website

No original slide deck, print manual, document template, email system, or mobile design system was established by this investigation. Applying the brand to those media requires design choices. Keep that boundary explicit: **verified ingredients, newly adapted composition**.

For any new medium, carry over the exact black/violet palette, white/gray text hierarchy, Terminus/Handjet division, original identity assets, measured border/radius/spacing relationships where units are meaningful, and the relevant compact labels. Preserve the relative role of these ingredients rather than claiming a new page size or layout is canonical.

| Request | Grounded starting point | What remains a new decision |
|---|---|---|
| Branded app/dashboard | Main panel/widget hierarchy, real status readouts, project/input/button families | Navigation architecture, responsive breakpoints, product-specific data models |
| CLI/TUI | Kitty ANSI palette, `//`/bracket/clock prompt grammar, Btop ramps for analogous metrics | New commands, row density, terminal compatibility |
| Document/deck | Handjet display, Terminus labels/text where readable, original logo, black/violet panels and dividers | Page/slide geometry, print conversions, minimum readable sizing |
| Static social/banner image | Original wordmark/avatar, pixel background family, palette, selective glow | Crop, composition, copy, platform dimensions |
| New desktop component | Active native colors, 1–2px outlines, per-app type/geometry | Component API, new interactions, toolkit fallback behavior |

If a new artifact needs larger type, reduced motion, keyboard focus, responsive stacking, or print contrast, implement the appropriate usability requirement. Label material changes as adaptations when discussing fidelity. The original site's smallest labels and viewport limits are observations, not a reason to make an inaccessible new artifact.

## Practical review questions

- Is the identity the original asset and correctly spelled, with its real proportions?
- Are primary, secondary, accent, and status colors serving a documented role?
- Does the output show the actual intended fonts, not merely name them in source?
- Are outer structure, nested surfaces, labels, and body text visibly distinct using the established hierarchy?
- Are shadows and motion local and proportional to the measured examples?
- Are third-party content, inherited native themes, and separate experience palettes kept in their real contexts?
- Are novel decisions presented as adaptations instead of invented brand rules?

These questions help apply the user's request; they are not a new approval process or a requirement to produce an audit report for every small edit.
